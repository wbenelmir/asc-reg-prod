# ADR-0016: Independent invitation and on-behalf claim token design

| Field | Value |
| --- | --- |
| Status | Accepted |
| Date | 2026-09-21 |
| Related requirements | Schema §6.3-§6.4; TRD `INV-001`; Phase 2 Prompt 2 domain correction |

## Context

`InvitationLink` and `OnBehalfClaim` each need an unguessable, revocable,
hashed-at-rest secret token (`INV-001`, TRD §16.1's authentication baseline).
Three existing key families already exist in this project, each purpose-built
and deliberately independent (ADR-0006, ADR-0007):

1. Identity encryption / blind-index keys (`IDENTITY_ENCRYPTION_*`,
   `IDENTITY_BLIND_INDEX_HMAC_*`) -- for NIN/passport/contact values that
   must later be recovered or matched deterministically.
2. Rate-limit HMAC keys (`RATE_LIMIT_HMAC_*`) -- for OTP throttling
   fingerprints, a wholly separate concern from identity matching.

An invitation link token and an on-behalf claim token are neither: they are
single-purpose, application-generated random secrets that are never
recovered (only compared) and never used for identity matching. Reusing
either existing key family would let rotating one silently affect the other
(exactly the cross-contamination ADR-0006/ADR-0007 already reject), and
neither family's key material is even the right shape for this purpose
(both are HMAC keys for keyed comparison of externally-supplied plaintext,
not for hashing a value this project itself generates).

## Decision

Invitation link tokens and on-behalf claim tokens use a third, independent,
**keyless** scheme:

1. Generate `secrets.token_urlsafe(32)` (256 bits of CSPRNG entropy) --
   never a shorter token, never a predictable or sequential value.
2. Persist only `hashlib.sha256(raw_token.encode()).hexdigest()` in
   `InvitationLink.token_hash` / `OnBehalfClaim.claim_token_hash`, each
   `unique=True`.
3. Return the raw token to the caller (embedded in the generated URL) only
   at creation or rotation time. It is never persisted anywhere, in any
   form, at rest -- not in the database, not in a log line, not in an
   audit-event payload.
4. Verification recomputes the SHA-256 of a caller-supplied token and looks
   it up by exact hash equality. No keyed comparison is needed: because the
   input token is itself independently CSPRNG-generated by this
   application (never externally supplied, unlike an email address or a
   NIN), a fast unkeyed hash cannot be dictionary-attacked or rainbow-
   tabled the way a keyed blind index protects a comparatively low-entropy
   real-world value.
5. No `.env` secret family is read or required for this scheme. Rotating
   `IDENTITY_ENCRYPTION_*`, `IDENTITY_BLIND_INDEX_HMAC_*`, or
   `RATE_LIMIT_HMAC_*` has zero effect on any invitation link or claim
   token, and vice versa.

## Consequences

- A leaked `InvitationLink`/`OnBehalfClaim` row (e.g. a database dump)
  never exposes a usable token -- only its SHA-256 hash, and the token's
  256 bits of entropy makes offline brute-force infeasible.
- No key rotation procedure is needed for this scheme: there is no key.
  Revocation is a `status` transition on the row, not a key-versioning
  operation.
- `OnBehalfClaim.intended_email_encrypted`/`intended_email_hash` use the
  EXISTING identity blind-index family (ADR-0006) deliberately, since that
  value genuinely needs later encrypted recovery and deterministic
  matching against the participant's verified OTP email -- only the claim
  *token* itself uses this ADR's independent scheme.
